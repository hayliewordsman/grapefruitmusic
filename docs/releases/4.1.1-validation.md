# Grapefruit Music & Podcasts 4.1.1 — build 48

A fix release for podcasts.

## Episodes that ended early (Deadline: White House)

The show's feed (feeds.simplecast.com/iDG4OTeq) serves each episode through tracking redirects to
Simplecast's ad injector, which stitches ads into the episode as it's served. Eight recent episodes
were downloaded as Grapefruit asks for them and compared frame by frame with the episodes as
published (no ads): every copy holds the whole episode, with ads in four places (before it, two
breaks, and 30 seconds after it). All are 128kbps, 44.1kHz stereo MP3 with no length header, and
Grapefruit's length estimate matches each copy's real length exactly.

Each day's show is two episodes, one per TV hour. A first hour ends as the TV hour does ("Deadline:
White House continues after this break"), then the 30-second ad, then the end of the file; the next
segment is the second hour's episode. So an episode that "stops before the last segment, right after
an ad" is the producers' cut, not Grapefruit's.

What was Grapefruit's: every request to the feed's address gets a newly stitched copy (three requests
for one episode answered 45,463,388, 45,473,420 and 45,233,929 bytes, with different audio at the
same byte). The stream relay asked the feed's address again for every seek and reconnect, so after a
pause, a seek or a dropped connection it read another copy from the same byte: the episode jumped,
repeated or ended in the wrong place. Where the redirects end is the copy's own address, which keeps
giving the same copy. Now the relay reads every request of an episode from there (PodcastAudio.Episode);
if that address has expired, it starts again from the feed's.

Checked against the real host (the 4.1.1 classes on a desktop JVM): four requests for "Laying out
plans to contest the election", one from the start and three part-way through, all read the same
43,593,021-byte copy, and the same range twice gave the same bytes.

## The crash starting an episode on the JP5S

Reported: on the JP5S (Android 4.2), starting a streamed Deadline: White House episode closed the
app; after a downloaded episode of another show had played, the same episode played. It couldn't be
reproduced here (no Android 4.2 device or emulator). Fixed in 4.1.1:

- The likeliest cause: a seek (a podcast resumes where it was left) read a different stitched copy,
  and on Android 4.x, Grapefruit's own engine decodes in the app's process, where inconsistent data
  from a stream can end the app. The pinning above removes that.
- Background work that only caught Exceptions now catches everything, so an Error there ends that
  work, not the app: Bg.run and Bg.execute, the artwork loader (it caught I/O errors and out of
  memory only), and the stream relay (it caught I/O errors only).
- CrashReport: a crash in Java code leaves a short report (app and Android versions, device model,
  stack trace, the last few things the app did, web addresses without query strings, file paths
  without names). The next start offers to share it; nothing is sent otherwise. A crash in Android's
  native code doesn't reach it.
